    % =========================================================
    \chapter{INTRODUCCIÓN}
    % =========================================================

    Los sistemas de software empresariales modernos registran de manera
    continua el comportamiento de cada transacción a través de archivos
    de \textit{log}. En una plataforma de reportes de ventas, cada solicitud
    de un usuario atraviesa múltiples capas de servicio —desde el módulo
    de generación de reportes hasta la base de datos— dejando rastros
    detallados sobre tiempos de respuesta, volúmenes de datos procesados
    y uso de recursos computacionales \citep{he2016experience}. El análisis
    sistemático de estos registros constituye una fuente de inteligencia
    operativa invaluable para los equipos de tecnología.

    Sin embargo, el volumen masivo de logs generados en producción hace
    inviable su inspección manual. Un sistema con 120 usuarios activos
    puede generar decenas de miles de entradas de log al mes, distribuidas
    en tres o más capas de servicio. En este contexto, la minería de datos
    ofrece mecanismos para automatizar la identificación de patrones
    inusuales, permitiendo que los sistemas de monitoreo alerten de manera
    proactiva sobre degradaciones de rendimiento, errores en cascada o
    comportamientos que ponen en riesgo la disponibilidad del servicio
    \citep{chandola2009anomaly}.

    La detección de anomalías no supervisada resulta especialmente adecuada
    para este dominio, ya que en entornos reales las instancias anómalas
    son escasas y raramente están etiquetadas con anticipación. El algoritmo
    \textit{Isolation Forest} \citep{liu2008isolation} se destaca en este
    campo porque no requiere una definición explícita de lo que constituye
    una anomalía: aprende la distribución del comportamiento normal y señala
    como anómalos aquellos registros que resultan difíciles de integrar en
    esa distribución.

    El presente trabajo aplica \textit{Isolation Forest} sobre 30\,000
    registros de logs de una plataforma de reportes de ventas compuesta
    por tres capas: \textit{Report Service}, \textit{Sales API} y base de
    datos. El objetivo central es no solo detectar los registros anómalos,
    sino también caracterizar los patrones que los distinguen del
    comportamiento normal, proporcionando información accionable sobre el
    tipo de problema que podría estar afectando al sistema.

    % =========================================================
    \chapter{DIAGNÓSTICO Y PLANTEAMIENTO DEL PROBLEMA}
    % =========================================================

    La plataforma de reportes de ventas analizada procesa solicitudes de
    usuarios con tres roles distintos —administrador, gerente y vendedor—
    que requieren cinco tipos de reportes: ventas diarias, ventas mensuales,
    ventas por producto, ventas por sucursal y ventas por cliente. Cada
    solicitud recorre el siguiente flujo de servicios:

    \begin{center}
    \textbf{Usuario} $\rightarrow$ \textbf{Report Service} $\rightarrow$
    \textbf{Sales API} $\rightarrow$ \textbf{Base de Datos}
    \end{center}

    Cada capa registra métricas operativas propias. El equipo de tecnología
    ha identificado que el sistema experimenta episodios periódicos de
    degradación que se manifiestan en incrementos abruptos de los tiempos
    de respuesta, aumento inusual en el volumen de datos procesados,
    elevación del consumo de CPU y memoria, y aparición de errores en la
    comunicación entre servicios. Estos episodios afectan la experiencia
    de los usuarios y, en casos extremos, provocan indisponibilidad del
    servicio.

    La organización cuenta con registros históricos de logs pero carece
    de un mecanismo automatizado para detectar y caracterizar estos
    comportamientos anómalos. Las variables operativas disponibles son
    de naturaleza independiente —no existe una variable de respuesta
    predefinida durante la operación normal— lo que orienta el análisis
    hacia un \textbf{modelo de aprendizaje no supervisado}.

    El conjunto de variables operativas disponibles incluye \textbf{10
    variables numéricas independientes} (sin contar las variables tipo
    factor) que superan el mínimo requerido de 5 para modelos no
    supervisados:

    \begin{enumerate}
        \item \textbf{Tiempo de respuesta del servicio} (\texttt{response\_time\_ms},
        ms): mide el tiempo total que tarda el servicio en procesar una
        solicitud. Es la causa directa de mala experiencia del usuario.

        \item \textbf{Tiempo de consulta a la base de datos}
        (\texttt{db\_query\_time\_ms}, ms): mide la latencia de las
        consultas SQL ejecutadas. Valores elevados indican ineficiencia
        en el motor de base de datos.

        \item \textbf{Tiempo de respuesta de la Sales API}
        (\texttt{api\_response\_time\_ms}, ms): latencia de la capa
        intermedia. Incluye el tiempo de consulta a BD más la lógica
        de negocio propia de la API.

        \item \textbf{Registros retornados} (\texttt{records\_returned},
        unidades): cantidad de filas de datos incluidas en el reporte.
        Valores extremadamente altos pueden señalar exportaciones masivas
        no autorizadas.

        \item \textbf{Filas escaneadas en BD} (\texttt{rows\_scanned},
        unidades): número de filas que el motor de base de datos procesó
        para generar el resultado. Una alta relación filas escaneadas /
        registros retornados indica consultas ineficientes.

        \item \textbf{Tamaño del reporte generado} (\texttt{report\_size\_kb},
        KB): tamaño del archivo de salida. Relacionado con el número de
        registros y la complejidad del reporte.

        \item \textbf{Uso de CPU del servicio} (\texttt{cpu\_usage\_percent},
        \%): porcentaje de CPU consumido durante el procesamiento de la
        solicitud.

        \item \textbf{Uso de memoria RAM} (\texttt{memory\_usage\_mb}, MB):
        memoria consumida durante el procesamiento de la solicitud.

        \item \textbf{Número de reintentos} (\texttt{retry\_count},
        unidades): cantidad de veces que la solicitud fue reintentada
        por fallos. Valores mayores a 1 indican inestabilidad.

        \item \textbf{Número de errores registrados} (\texttt{error\_count},
        unidades): errores generados durante el procesamiento de la
        solicitud.
    \end{enumerate}

    Adicionalmente, el conjunto incluye \textbf{variables tipo factor}:
    \texttt{service} (servicio que generó el log), \texttt{report\_type}
    (tipo de reporte) y \texttt{user\_role} (rol del usuario), que
    se incorporan al modelo mediante codificación numérica.

    \section{PLANTEAMIENTO DEL PROBLEMA}

    \textbf{Pregunta de investigación}

    ¿La aplicación del algoritmo \textit{Isolation Forest} sobre los
    registros operativos de la plataforma de ventas —que integra los
    servicios \textit{Report Service}, \textit{Sales API} y base de
    datos— permitirá detectar y caracterizar comportamientos anómalos
    en las métricas de rendimiento del sistema, identificando
    potenciales problemas de disponibilidad y degradación del servicio?

    \section{OBJETIVO GENERAL}

    Detectar y caracterizar comportamientos anómalos en los registros
    operativos de una plataforma de ventas mediante la aplicación del
    algoritmo \textit{Isolation Forest}, con el propósito de identificar
    potenciales problemas de rendimiento y disponibilidad del sistema.

    \section{OBJETIVOS ESPECÍFICOS}

    \begin{enumerate}
        \item Describir las características estadísticas y distribuciones
        de las variables operativas del sistema de reportes de ventas para
        identificar los rangos de comportamiento normal en los tres
        servicios de la plataforma.

        \item Construir un modelo de detección de anomalías basado en el
        algoritmo \textit{Isolation Forest}, ajustando el hiperparámetro
        \textit{contamination} mediante el conjunto de validación para
        maximizar el F1-Score.

        \item Evaluar el desempeño del modelo sobre el conjunto de testeo
        utilizando las métricas AUC-ROC, F1-Score, precisión y recall.

        \item Caracterizar los comportamientos anómalos detectados por el
        modelo, identificando los tipos de anomalías más frecuentes y
        las variables operativas con mayor poder discriminativo.
    \end{enumerate}

    \section{FUENTE DE DATOS}

    Los datos utilizados en este trabajo provienen de los registros
    operativos de una \textbf{plataforma privada de ventas empresarial},
    cuyos logs fueron anonimizados antes de su análisis. En cumplimiento
    con los principios de protección de datos, los identificadores sensibles
    fueron sustituidos por su función hash unidireccional:

    \begin{itemize}
        \item \textbf{Usuarios}: reemplazados por \texttt{user\_hash}
        (formato: \textit{user\_NNN}).
        \item \textbf{Empresas/Tenants}: reemplazados por
        \texttt{tenant\_hash} (formato: \textit{tenant\_NNN}).
        \item \textbf{Identificadores de traza}: generados mediante UUID
        truncado (\texttt{trace\_id}), sin relación con identificadores
        internos del sistema.
    \end{itemize}

    El conjunto de datos comprende \textbf{30\,000 registros} de logs
    recopilados durante el mes de enero de 2026, distribuidos
    uniformemente entre tres servicios (10\,000 registros cada uno).
    Estos registros corresponden a \textbf{10\,000 trazas únicas}, cada
    una representando una transacción completa de usuario a base de datos.
    El sistema registra actividad de \textbf{120 usuarios únicos}
    distribuidos en \textbf{20 tenants}.

    \section{PROCESO DE MODELADO}

    \textbf{Método y tarea.} Se empleó el algoritmo
    \textbf{Isolation Forest} \citep{liu2008isolation, liu2012isolation},
    un método de aprendizaje no supervisado diseñado específicamente para
    la detección de anomalías. Su fundamento es el principio de
    \textit{aislamiento}: las anomalías son instancias atípicas que se
    aíslan con mayor facilidad que las instancias normales al particionar
    aleatoriamente el espacio de características. El algoritmo construye
    un conjunto de $T$ \textit{árboles de aislamiento} (\textit{isolation
    trees}) y asigna a cada instancia una puntuación de anomalía basada
    en la profundidad media a la que es aislada:

    \begin{equation}
        s(x, n) = 2^{-\frac{E[h(x)]}{c(n)}}
    \end{equation}

    donde $h(x)$ es la longitud del camino de aislamiento de la instancia
    $x$, $c(n) = 2H(n-1) - \frac{2(n-1)}{n}$ es el factor de
    normalización (siendo $H$ la función armónica), y $E[\cdot]$ es el
    promedio sobre todos los árboles. Valores de $s$ cercanos a 1
    indican anomalía; cercanos a 0 indican normalidad.

    en tres subconjuntos mediante muestreo estratificado (manteniendo
    la proporción de anomalías en cada partición):

    \section{EVALUACIÓN}

    Para medir la calidad del modelo sobre el conjunto de \textbf{testeo},
    se emplearon los siguientes indicadores \citep{fawcett2006introduction}:

    \begin{itemize}
        \item \textbf{AUC-ROC} (\textit{Area Under the ROC Curve}): área
        bajo la curva que relaciona la tasa de verdaderos positivos (TPR)
        con la tasa de falsos positivos (FPR) para todos los umbrales
        posibles. Mide la capacidad discriminativa del modelo de manera
        independiente del umbral, con valores entre 0,5 (aleatorio) y
        1,0 (perfecto).

        \item \textbf{Precisión}: fracción de los registros predichos
        como anomalía que efectivamente son anomalías.
        $\text{Precisión} = TP / (TP + FP)$.

        \item \textbf{Recall} (sensibilidad): fracción de las anomalías
        reales que fueron correctamente detectadas.
        $\text{Recall} = TP / (TP + FN)$.

        \item \textbf{F1-Score}: media armónica entre precisión y recall.
        $\text{F1} = 2 \cdot \text{Precisión} \cdot \text{Recall} /
        (\text{Precisión} + \text{Recall})$. Métrica principal de
        ajuste de hiperparámetros dado el desbalance de clases.

        \item \textbf{Matriz de confusión}: tabla de contingencia con
        los conteos de verdaderos positivos (TP), verdaderos negativos
        (TN), falsos positivos (FP) y falsos negativos (FN).
    \end{itemize}

    \chapter{CONCLUSIONES}
    % =========================================================

    Las siguientes conclusiones responden a cada objetivo específico
    planteado y se vinculan al problema de investigación central:

    \begin{enumerate}
        \item \textbf{Respecto a describir las características estadísticas
        del comportamiento normal (Objetivo Específico 1):} El análisis
        exploratorio reveló que, en condiciones normales, el tiempo de
        respuesta del \textit{Report Service} se sitúa entre 933 ms y
        3\,754 ms (percentiles 0 y 75), con una mediana de 3\,084 ms.
        Las variables de tiempo presentan altas correlaciones entre sí
        ($r > 0.9$), lo que confirma la naturaleza en cascada del
        sistema. La tasa de anomalías es estable a lo largo del día
        ($\approx 4,5\%$), descartando dependencias temporales y
        apuntando a causas sistémicas. Este conocimiento del
        comportamiento normal es el insumo clave para la construcción
        del modelo de detección.

        \item \textbf{Respecto a construir el modelo Isolation Forest
        (Objetivo Específico 2):} El modelo fue construido exitosamente
        con 14 variables de entrada, entrenado sobre 21\,000 registros
        y ajustado mediante 8 valores candidatos de \textit{contamination}
        evaluados en el conjunto de validación. El valor óptimo
        (\texttt{contamination = 0,04}) maximizó el F1-Score de
        validación (0,6785), priorizando la precisión sobre el recall
        al ser conservador en la declaración de anomalías, lo cual es
        adecuado en contextos operacionales donde las falsas alarmas
        tienen costos relevantes.

        \item \textbf{Respecto a evaluar el desempeño en testeo (Objetivo
        Específico 3):} El modelo alcanzó un \textbf{AUC-ROC de 0,9696}
        sobre el conjunto de testeo independiente (4\,500 registros),
        evidenciando una capacidad discriminativa excelente. El F1-Score
        de 0,7016 con una precisión de 0,7528 y un recall de 0,6569
        indica que de cada 100 alertas generadas por el modelo, 75 son
        anomalías reales, y el modelo detecta el 65,7\% del total de
        anomalías presentes. La tasa de falsa alarma es del 1,0\% (44
        falsos positivos sobre 4\,296 registros normales), nivel
        aceptable para un sistema de monitoreo en producción.
        Estos resultados responden afirmativamente a la pregunta de
        investigación: el algoritmo Isolation Forest sí permite detectar
        comportamientos anómalos en los registros de la plataforma.

        \item \textbf{Respecto a caracterizar los comportamientos anómalos
        (Objetivo Específico 4):} El análisis de perfiles reveló que cada
        tipo de anomalía deja una firma estadística distintiva en las
        variables operativas. Las consultas lentas a la base de datos
        elevan el tiempo de consulta BD entre 8 y 20 veces; las
        exportaciones grandes incrementan el volumen de registros en
        10 a 30 veces; la alta tasa de errores se distingue por valores
        no nulos en \textit{error\_count} y \textit{retry\_count}; y
        el alto uso de recursos eleva el CPU por encima del 85\%.
        Las variables con mayor poder discriminativo son los tiempos de
        respuesta (\texttt{api\_response\_time\_ms} y
        \texttt{response\_time\_ms}) y las variables de volumen
        (\texttt{records\_returned} y \texttt{report\_size\_kb}),
        información que permite diseñar umbrales de alerta específicos
        para cada tipo de problema de disponibilidad o rendimiento.
    \end{enumerate}

    En conclusión, la aplicación de \textit{Isolation Forest} sobre los
    registros operativos de la plataforma de ventas demostró ser una
    herramienta efectiva para la detección automatizada y caracterización
    de comportamientos anómalos, con potencial de implementación como
    sistema de monitoreo en tiempo real para identificar oportunamente
    problemas de rendimiento y disponibilidad.
